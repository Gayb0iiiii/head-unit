# User-requested software updates

This implementation is published on `feat/orangepi-system-ui` starting at `0655338901d933290c89be1a06889237de0914bf`. It has not been installed on the Orange Pi. A native Cage/Electron/WayVNC trial remains required before anyone enables this at boot. The local HDMI launcher and the separate headless WayVNC manual wrapper are documented in [orangepi-system-ui.md](../deployment/orangepi-system-ui.md).

## Flow

The existing kiosk launcher keeps its cruiser, ARM64, DRM, Cage and Electron checks. It starts Cage with a persistent unprivileged Node child (`deployment/electron-supervisor.mjs`). That child launches Electron with an IPC channel and retains the same Wayland display while Electron is replaced. It records the active commit in `~/.local/state/headunit/release.json` with owner-only file mode. Releases live in `~/.local/state/headunit/releases/<commit>`; the current source checkout remains untouched. No privileged helper, display manager, or boot policy is added.

Settings → Software update has a two-step parked confirmation. The host accepts only a boolean confirmation from the trusted sandboxed renderer; it accepts no command, path, URL, branch or SHA. Update is disabled when motion is known to be moving. No vehicle motion provider is currently installed, so an unknown state relies on the person's explicit parked confirmation. No update runs at startup.

The host checks both the literal and effective `https://github.com/Gayb0iiiii/head-unit.git` origin (including Git `insteadOf` rewrites) and local `feat/orangepi-system-ui` branch, requires clean source and active worktrees, fetches that fixed branch and requires its commit to descend from the active one. A detached worktree is tested with `npm test` and built with `npm run build`; there is no root `package-lock.json`, so `npm ci` is deliberately absent. A completed release can be retested after an interruption. A disposable staging worktree is used for new releases, so an interrupted build cannot overwrite the active build. Git hooks and fsmonitor are disabled for the updater's Git calls. Git and build commands run in isolated unprivileged process groups so cancellation and timeouts stop descendants that remain in that group before the operation settles.

After staging, Electron requests activation from the persistent supervisor. The supervisor validates the fixed SHA release path, records a pending update atomically, stops the old Electron and starts the candidate. A ready message is sent only after the trusted renderer initializes and the Electron window is shown. Candidate startup has a 30-second readiness deadline and a further 10-second health period. Failure before commitment rolls back to the old release while Cage stays alive. If power is lost with an update pending, the next launch clears pending and boots the prior recorded release. The recovered Settings page reports the failed update. Repeated crashes of the active release stop the supervisor, allowing the existing service/getty recovery path. The display, touch, WayVNC, network and source update behavior have **not** been verified on the Orange Pi.

Settings can cancel fetch or build before activation. Once activation starts, the supervisor owns rollback. A completed build is never presented as a working release before the window has passed readiness and the health period. The UI reports an error and remains usable if fetch, tests, or build fail. Status messages are intentionally coarse; no remote output or system paths reach the renderer.

## Review and device gates

Cloud checks cover fixed-branch/dirty/diverged rejection, failed build cleanup, concurrent requests, cancellation, IPC sender and argument validation, startup failure, health-window failure, power interruption, rollback and a real Node child-process IPC switch fixture. Node 24 is the development baseline. An isolated official Node 22.22.2 x86_64 binary passed 516 tests, the build, and the real-child supervisor fixture. These checks do not run native Electron, Cage, WayVNC or the Pi display stack; ARM64 Node 22.22.2 still needs a device run.

Before any device rollout, review the source diff and the exact origin/branch, then run the repository tests/build on the Pi without `npm ci`. Start from a local tty using the existing manual launcher, verify the Settings action with an intentionally prepared newer test commit, verify the WayVNC session stays connected across Electron restart, and verify both successful activation and rollback. Confirm the compositor, touch, keyboard and mouse still work. Keep a second local tty or SSH path available. Do not enable or change the boot service until those checks pass.

For recovery, return to a tty, stop the optional `headunit-ui.service` if it was separately enabled, and use a separate worktree at the last verified commit; build it before manual launch. The direct-launch revision `bc2f98fe8f7ef8449cb116b45c25ddd537fe7897` bypasses the new supervisor for an emergency manual display trial. The updater does not change the service or credentials. Treat `release.json` and releases as recovery records; do not delete them during an in-progress update. If the supervisor cannot validate the recorded release, it exits rather than selecting an unverified build.

Remaining risk: the current health signal proves renderer initialization and `BrowserWindow.show()` was invoked, not that physical pixels, touch or WayVNC are working. A remote source commit can execute its own test/build scripts after the user requests an update; repository write access remains the software supply-chain trust boundary. Detached staging directories from abrupt process death may remain under the state directory and require reviewed cleanup, but do not replace the active release.
